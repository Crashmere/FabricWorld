# Verification Principles and Known Limitations

Routine verification covers only the current change and uses isolated synthetic data; see [DEPLOYMENT.md](DEPLOYMENT.md) for the specific release and rollback procedures. Historical regression suites and per-run test-case counts have been retired; the original records remain available in Git history.

Image processing depends on libvips. When a change affects images or backups, verify the relevant input formats, output readability, and database/photo consistency. A real device is required to confirm phone-camera behavior, HEIC export from the photo library, and the soft keyboard; a desktop mobile viewport cannot substitute for real-device results. Standard photos have a maximum long edge of 2560 px; original camera files are not retained.

Photo-rotation validation on 2026-11-21 used an isolated synthetic database and asymmetric color-quadrant images. JPEG and WebP pixel direction, dimensions, photo order, unchanged record fields, history, idempotent replay, stale revisions, and unbound-copy binding passed. The source JPEG and a hard-linked backup retained their bytes after rotation. Desktop Chrome and phone-sized WebKit passed detail-page persistence, draft-only rotation, final form save, and rotated fit/zoom. A simulated lost commit response and failed operation lookup were retried with the same key and body, producing only one record revision. Real phone-camera acceptance remains unverified.

The active application runs on `nas`, with HTTPS and centralized device authentication through its LAN entrance and the `vps` gateway. Routine backups are agent-operated full compressed packages on external storage; native daily timers are disabled. Temporary local upgrade protection is removed only after runtime and affected-data acceptance. Preserved `ali` and maintenance-computer archives cover historical states, not later NAS writes; consult the [shared inventory](https://github.com/Crashmere/agent-config/blob/main/skills/server-operations/references/current-state.md) for actual external-backup readiness. Read the running version from `current-commit` and documentation provenance from `docs/SOURCE`, and check service state live.

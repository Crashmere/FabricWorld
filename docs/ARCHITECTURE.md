# Architecture and Business Rules

Browser → Nginx `/fabricworld/` → Go `127.0.0.1:18082` → independent SQLite database and image files. The Vue 3/TypeScript/Vite frontend is embedded in the Go program. The server processes images through the libvips command line and does not run a persistent Node application.

## Fabrics and Remnants

One record represents one batch of fabric. Materials and tags are deduplicated string arrays, and location is text. There are no application users, identities, or personal libraries. Width and length may be unknown; values are entered in cm/m and converted to integer millimeters. Piece count is 1–999, with at most 50 groups per record. Unknown is not 0. An irregular remnant records its maximum width and length plus a note; dimension filters match only complete rectangles. The total purchase price is parsed into integer cents and does not decrease as remnants shrink.

Material names continue to support filtering. Percentages are stored independently in the `materialPercentages` map and are not embedded in the name or composition note. A single selection defaults to 100%. When a second material is added to a single selection, clear the former default and leave both percentages empty; when a third is added, preserve already entered percentages. With multiple selections, each item has a small optional input before it. Preserve decimal strings exactly; do not validate the total, balance values automatically, or round them. Deselecting a material removes its percentage; when one remains, restore 100%. Existing multi-material records keep unknown percentages, and explanatory text is not parsed automatically. Details, lists, history, copies, and exports all preserve percentages. Updating a remnant does not modify them.

Material management derives names and usage counts from current fabric records, including used-up and recycle-bin records; the same name counts only once per fabric, and recycle-bin usage is shown separately. `material_catalog` stores names added independently from the management page together with random identities, allowing zero usage. The catalog merges this table with names present in current fabrics, while counts are always calculated live from fabrics. An unused built-in option that was not added independently does not appear in management. The editor offers built-in options, names added to the catalog, saved custom materials, and the current selections. Removal matches the name exactly and removes it in one operation from every related fabric and percentage map. If one material remains, set it to 100%; if several remain, preserve their percentages. Fabrics, photos, composition notes, and other details remain unchanged, and history snapshots remain available. A name arising only from fabric usage leaves the list after its last use disappears; an independently added name remains until explicit removal. Removal also deletes the catalog entry. A built-in option can still be selected again.

Statuses are `unused`/`using`/`used`. An in-stock state has at least one fabric piece; `used` must have none. On the details page, the exact action `编辑资料` manages photos, materials, and other details; dimension and status correction is collapsed by default. Ordinary editing does not change status automatically.

The exact action `更新余料` appears beside remaining dimensions on the details page and opens the dedicated `/fabrics/:id/remnant` page, where the user enters only remaining pieces or selects `已经用完`. Saving a remnant changes the status to `using`. Marking it used up requires a second confirmation and clears the current pieces. Switching the option or canceling confirmation preserves unsubmitted dimensions. Used-up records hide the remnant entry; entry mistakes can be corrected under `编辑资料`. The server-side `remnant` action changes only `pieces`/`status`, preserving all details and image references as well as `revision`, idempotency, and change-history checks. Old `edit?mode=remnant` links redirect to the new page. When an old client submits the complete form, a remnant action ignores all other fields.

Copying carries only name, materials, composition, color, tags, location, and notes. It does not copy images, dimensions, or purchase information.

The list defaults to in-stock records ordered by most recent purchase date, falling back to entry date, with 24 items per page. Queries run on the server and match name, material, tags, composition, notes, shop, and location. Material, color, location, and tag filters are exact. One fabric piece must satisfy all dimension conditions. Counts cover the complete filtered set, while overview statistics cover the entire non-deleted library.

## Finished Sewing Works

The finished-work library uses independent `works`/`work_changes` records for name, photos, category, completion date, pattern, size, recipient, tags, and making notes. It has a many-to-many source relationship with fabrics and does not change fabric inventory or `revision`. Fabric-usage notes are text; the user continues to update remnants manually from fabric details. The server saves source-name snapshots, so deleting a fabric preserves the finished work and source description. Finished works support independent drafts, version conflicts, idempotent writes, history, a 30-day recycle bin, and CSV/ZIP export. See [WORKS.md](WORKS.md) for pages, field limits, and migration design.

## SQLite and Writes

Schema v1, `application_id` 1178681932; WAL, foreign keys, `FULL` synchronization, a five-second busy timeout, and one connection. `fabrics` stores bounded business JSON together with search columns. Nested pieces are stored in JSON and queried with JSON1. `media` independently maintains file references, `changes` records the before/after business snapshots for every modification, and `operations` stores idempotent results.

Every fabric write checks `revision` and updates the fabric, photo ownership, change history, and idempotent result in one transaction. The same idempotency key and request fingerprint return the previous result; reusing a key for a different request returns 409. Image processing does not occupy a write transaction. Image uploads also have idempotent results checked by content digest. Ordinary operation records are retained for seven days; an expired unknown result is not retried automatically.

Bulk material removal uses the catalog's random identity, if any, plus a digest of the ordered ID/`revision` set of related fabrics as `version`. Recheck it at submission. If a related record has been added, modified, deleted, or restored, return 409 and require refresh and reconfirmation. Commit every related record's `revision`, update time, `remove_material` history, and idempotent result in one transaction. Any failure rolls back the entire operation and does not change photo ownership. Both addition and removal query the original operation result first, preventing a stale addition retry from recreating a name removed later or a stale removal retry from deleting a newly re-added material. A unique name constraint ensures concurrent duplicate additions retain only one entry. Re-adding generates a new random identity, so a stale removal request for a zero-use entry also conflicts.

The Ledger integration receives transaction ID, title, date, and total price through the dedicated `/api/integrations/ledger` endpoint. The first 16 bytes of the SHA-256 digest of `ledger:<UUID>` become the stable operation key, and the fingerprint uses the same source string. Source deduplication and fabric creation commit in the same transaction. These `operations` are not removed by the seven-day cleanup and are restored with database backups. Even after a fabric is edited or deleted, a retry neither creates nor overwrites it. Read the current fabric before returning; when it has been deleted, instruct the caller to inspect or restore it. Ledger integration does not change the schema. The fabric-name limit is 500 characters to match Ledger titles.

Service startup requires an existing database with the correct identity, schema, and integrity. First installation uses explicit `init`; a missing or damaged database must not cause automatic creation of an empty one. `migrate` explicitly adds the independent material catalog, finished-work and history tables, `media.work_id`, indexes, and photo-protection triggers while retaining `user_version=1` and the existing fabric-record format. `check` and `serve` require compatible extensions; if a table or column is missing, they tell the operator to back up and run `migrate` rather than creating schema implicitly at startup. First-time `init` includes these structures directly, and backups cover the complete database. After restoring an old backup, explicitly run `migrate` and then `check`. The old program can still operate on fabrics; see [WORKS.md](WORKS.md) for old-version cleanup protection and rollback boundaries for finished-work photos.

## Image Lifecycle

Files are limited to 25 MiB and 80 MP, with at most 10 images per record. Validate content signatures and accept JPEG, PNG, WebP, HEIC, and HEIF. Reject SVG and animated PNG/WebP. For HEIC, libheif selects the primary image. libvips automatically normalizes orientation, emits an sRGB JPEG with a maximum long edge of 2560 px at Q88 and a 640 px WebP thumbnail at Q80, and removes metadata. Original uploads are retained only temporarily.

Images stream to disk one at a time. There is one global processing slot; return 429 when busy. Decoding has a 40-second timeout. Generated files use random IDs. Commit a `media` row only after the file is completely written and synchronized to disk. Permanent files are immutable. A staged image may be bound within 24 hours. A photo belongs to only one fabric or finished work, and `fabric_id`/`work_id` are mutually exclusive. Removed photos are retained for 30 days. Deleted fabrics and finished works enter their respective 30-day recycle bins. Maintenance deletes expired references and reclaims orphaned files and temporary directories that are at least 24 hours old.

Native backup and cleanup use a cross-process `flock`. Uploads and ZIP exports hold a shared lock; native backup and cleanup hold an exclusive lock and return an explicit busy message on conflict. The native command uses `VACUUM INTO` for a consistent snapshot, enumerates that snapshot's images, and creates hard links plus a SHA-256 manifest. Image immutability makes same-disk hard links stable. A native backup may briefly make a new upload return busy, while ordinary record reads and writes continue. This compatibility format includes unexpired staged images, removed images, and recycle-bin references.

NAS routine backups instead pause business writers and cold-copy complete data/config/program state to verified external storage, resume previously running services, then compress and verify that immutable copy. No native backup timer, internal routine staging, or automatic backup rotation runs on NAS. The NAS migration gives existing application cleanup its own `fabricworld-cleanup.service`/`.timer`, without generating snapshots or changing media/operation eligibility. Shared maintenance and deployment locks coordinate that writer with backups and upgrades. Upgrades use complete private `/var/lib/server-upgrades/fabricworld/<release>/` protection, removed only after runtime and affected-data acceptance; [OPERATIONS.md](OPERATIONS.md) defines the units and links to actual activation.

The initial media quota is 5 GiB; reject uploads when the root disk has less than 5 GiB free. The application's systemd total-memory limit is 640 MiB, `CPUQuota` is 100%, and image processing uses one thread. The quota includes staged and removed files represented in the `media` table. Operations must still inspect actual disk and backup retention with `df`/`du`; the quota is not whole-disk isolation. Per IP, allow 120 writes per minute and 30 uploads per minute separately. Only a loopback proxy may supply `X-Real-IP`.

## Browser

The header places the brand, the exact section switch `布料库` / `成品集`, and the hamburger menu on one row. Every page retains the top-bar switch; `成品集` no longer appears in the More menu. The menu contains only the recycle bin and `/materials` material management. Clicking the brand returns to the fabric library. The menu closes on outside click, focus leaving, route change, or Escape. Arrow Down can open it and focus the first item. The add-material entry is always at the top of the material-management page; the user enters a name directly without first searching. Blank or existing names cannot be submitted again. After a successful addition, show the material and usage count; a zero-use name can still be removed later. The management page also provides search and removal confirmation. Fabric create/edit pages only select existing materials and enter percentages. When an addition or removal result is unknown, store the original request and idempotency key in `sessionStorage`, allowing lookup or retry with the original key; after refresh, recover the operation result first. A version conflict refreshes the list and requires a new selection.

Material percentage, width, length, and total purchase price use `type=text`, `inputmode=decimal`, and `autocomplete=off`, requesting a phone numeric keyboard with a decimal point while preserving string-input precision. Piece count continues to use the integer numeric keyboard. The actual keyboard layout depends on the system and input method; a desktop WebKit mobile viewport cannot verify the real phone keyboard.

Simple sorting, filters, statuses, units, and editable suggestions consistently use `ChoiceField`. `DropdownPanel` positions the custom panel in the top layer while preserving dialog focus boundaries. Controls support keyboard, touch, and reduced-motion settings; see [CONTROLS.md](CONTROLS.md) for exact behavior. Complex controls such as dates and times retain system pickers.

Purchase date retains the native `date` control. Put borders, padding, and focus styling on the outer `date-input`; give the inner input zero border and zero padding. This avoids [WebKit 301648](https://bugs.webkit.org/show_bug.cgi?id=301648), where iOS adds padding to a 100%-width control. On phones, date and total price each occupy one row; on desktop they are side by side. Setting only `max-width` or changing to a single column does not resolve this native-control issue.

The site uses a layered fabric-swatch icon on a forest-green background. Ivory, sage-green, and terracotta swatches, pinked edges, stitching, and weave texture convey fabric. The header and browser share `web/public/fabricworld.svg`; ICO supplies 16/32/48 px images, and the Apple Touch icon is 180 px. After modifying the SVG, run `npm --prefix web run icons` with the existing libvips to regenerate both bitmap files. Asset paths use Vite `BASE_URL` so subpaths and detail-page refreshes work. Icon URLs in `web/index.html` and `web/src/App.vue` share the `v=swatches` version parameter; update both during a redesign to refresh the browser's icon cache.

The camera input uses `capture=environment`, separate from multi-select photo-library input. The phone system chooses the camera. The application does not use `getUserMedia`, a Service Worker, or offline synchronization. Uploads use XHR to show progress and retry failed images individually. A record cannot be saved while an image is incomplete; retry or remove it first.

Fabric and finished-work details, create, and edit pages share the `PhotoViewer` full-image component. It fills the available viewport on phones and keeps only a 12 px outer margin on desktop. Initially, the image fits the window; 100% means the size at which the whole image is visible. Users can zoom to 600% with plus/minus buttons, the wheel, or a pinch gesture. Double-click toggles between 200% and fit-to-window. A zoomed image can be dragged, with panning constrained at its edges. When the image region has focus, +/- zooms, arrow keys pan, and 0 resets. The exact button `适应窗口` restores the complete image at any time. Only the image region captures touch zooming and the wheel; browser page zoom remains unchanged. Changing photos, changing the image URL, or resizing the window resets the view. The details page retains Previous/Next navigation.

Uploaded photos read the standard main image. Photos still uploading or whose uploads failed use a local object URL. After upload finishes, an actively previewed local image switches to the server main image before its object URL is released. A local format the browser cannot decode shows an explanatory placeholder; after upload, the converted image can be viewed. Previewing does not submit the form. After the Close button, Escape, or desktop outside-overlay click closes the viewer, preserve input and restore original focus. Separate controls still handle removal, ordering, and upload retry. Tab navigation inside the dialog skips disabled and hidden controls.

Text and successfully uploaded references are stored in `sessionStorage` and can be recovered for 24 hours. An edit draft must match the server `revision`. Unuploaded `File` objects cannot be recovered after refresh. Clear the draft only after a successful save. After creating a fabric, including a copy, return directly to the home page; after editing an existing fabric, return to its details page. For an unknown write, query `operations` first; after confirming success, use the same navigation rule. Identical content may be retried with the original key. Render user data as plain text. Origin checks, CSP, `nosniff`, and request limits reduce cross-site and file risks but are not identity authentication.

The remnant page stores its draft separately from the details-edit draft. Before saving, record the original idempotency key. If refresh finds an unconfirmed write, query the operation result before discarding anything, even if the server `revision` has advanced. A confirmed-unsubmitted draft from an old version must not overwrite dimensions from a new version.

CSV prevents formula injection. ZIP streams records and standard main images from the current filters. It defaults to in-stock records and can include used-up ones; it excludes the recycle bin. Export is not a database recovery format, and there is no web import.
